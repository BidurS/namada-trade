Review notes (S3, 2026-10-29): the book's tick totals are the contract's decimal fields and are compared at 18 places (a fraction is a difference with the figures, not a thrown error), and each invariant's comparison is guarded so a check that cannot read an answer is 'not compared' with the error; the hour's writes wait for the depth minute of the same tick (`cron.ts` passes the minute's promise as `writeAfter`) and go on kv `depth.budget` and `depth.params` read again, so neither job's kv write is lost and the C3 counter is exact; kv `depth.owners` is held under `caps.ownersKvMax` (200 KB, plan 1.5) by leaving out the smallest owners' items by halves (their totals and counts stay), then the provenance list, with the note first in the row and in the owners health row; kv `depth.rolled` is the hour whose rollup last went in, separate from the once-an-hour marker `depth.hourly`, so an hour spent at the row cap is rolled into `depth_hourly` once inserts resume (within the six-hour catch-up); the window, the closing stretch and `hoursToRoll` are `series.ts`'s own, imported, not copied. Build notes (S4, 2026-10-29): the routes are a Hono sub-app built for one configuration (`worker/src/api-depth.ts` depthAppFor; the quote names the base coin's symbol from it and nothing else names NAM). `/api/depth/quote` walks the pool models rebuilt from kv `depth.states` on the stored curve's grid rebuilt at full precision from the stored reference (held digit for digit to the stored prices), then again on 32 points between the two grid prices the fill fell between, so the stored sizes come back within a hundredth of a percent of the minute's own answers and the split by pool is exact; without the states the stored aggregate curve alone is walked and the split is empty, said in `how`. The full grid itself (2,978 points) would cost about 120 ms a quote in Node against 33 ms for the thinned one, so it is not walked. `/api/depth/history` sends its range read and the pool's first stored step as one batch (two primary-key searches, one round trip), lists every missing step as a gap up to what the writer has had time to write, and never past the row cap. `/api/depth/heat` at seven days keeps the last minute of each five in the statement (`minute % 300000 = 240000`), so 2,016 rows come back of the 10,080 in the window. `/api/depth/changes` reads every pool's rows on the ts index and one pool's on the (pool_id, ts) index of migration 0014 (the S4 review found the pool filter walking the ts index through every other pool's rows; `pool=all` is refused, since a change belongs to one pool), each named so nothing is sorted, and reads a millisecond that a page cuts whole in a second round trip (a minute's diff writes every row at one ts). A parameter a depth route does not list is refused, not ignored. The edge keeps the minute, its quotes, the history and the changes 30 s, the heat a minute, the owners five minutes; a quote's size is rounded to three significant digits in the key, and the answer carries the size answered only (the route runs on the key's URL, so a "size asked" field could never hold what the reader typed; the S4 review dropped it). A stored read's provenance line names the table and the key range with no URL; the history's retention sentence takes its days from the configuration; a window holding exactly the row cap is complete, not cut; a missing hour is a gap fifteen minutes after its close. | `worker/src/depth/budget.ts`, `worker/src/depth/config.ts`, `worker/src/depth/index.ts`, `worker/src/depth/diff.ts`, `worker/src/depth/archive.ts` |
